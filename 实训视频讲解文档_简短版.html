三性六讲讲解 · 简短版（约 3 分钟逐字稿）

项目：山水有约 · 多 Agent 文旅行程规划系统 | 已生成 456+ 份真实行程书 | QPS 572 / P95 94ms / 8 并发 100% 成功 / 断点 5 秒恢复

【开场 15 秒】 我做的是一套生产级 AI 行程规划系统：不是聊天机器人套壳，而是把 AI 生成改造成可审计、可恢复、能防攻击的流水线。28 个服务模块、12 个 Agent、35 个 REST 端点。

【讲需求 20 秒】 三个真实痛点：LLM 算不准预算、分钟级链路崩了全白烧、注入攻击和超预算没人拦。toC 一句话生成 7 页签行程书，toB 给旅行社 9 页签审核工作台——和飞猪、携程程星途的主流架构同构，但多了全链路留痕和私有化部署。

【讲难点 25 秒】 五个难点：①LLM 是概率采样器，算术必然翻车；②任务状态在进程内存里，重启即丢；③大模型分不清指令和数据，网页夹带"忽略之前所有指令"就中招；④连点/重试导致重复审批，真金白银资损；⑤多 Agent 并发写同一份产物，出现半截文件。

【讲解决 60 秒】 对应五套方案，代码都在 backend/app： - 职责分离：LLM 只管创意，预算和时空校验全用确定性 Python（budget.py 双口径、validator.py haversine 距离）； - 服务无状态、任务有状态：每节点 checkpoint 落盘，11 态状态机，重启 5 秒内断点续跑，不重烧 token； - 三层防注入：8 个高危模式直接拦截挂起，4 个中危清洗放行，Agent 输出还递归扫描防"输出即注入"（safety_service.py）； - 幂等三件套：request_hash 去重 + 乐观锁 409 + Redis 分布式锁，重复审批必然冲突； - 原子写四步：tmp → fsync → 原子改名 → sha256，读方永远只见全旧或全新（atomic_writer.py）。

【讲优化 35 秒】 五轮"问题→解决→出新问题"连环优化：同步改异步 → 内存态改 checkpoint → 各写文件改 Reporter 单点原子写 → LLM 全包改职责分离 → 加幂等和分布式锁。压测两轮对比：健康检查 QPS 295 → 572，P95 从 264ms 压到 94ms；首页 gzip+缓存后 QPS 138 → 350。增量重规划复用前序节点，省 23% 生成量。

【讲双新 25 秒】 新技术：MCP 已真实接入飞猪门票链接，A2A 和 DeepSeek-R1 换模型零代码改动；新版本：Redis 8 的 Vector Set 让队列和向量检索收敛到一个组件，pgvector 0.8、LangGraph 1.0 与我的 checkpoint/HITL 设计同构。Python 3.13 评估后暂缓——生态没跟上就不追新。

【收尾 10 秒】 一句话总结：这套系统证明了 AI 应用从 demo 到生产的距离，就是状态机、幂等、原子性和安全边界这四件工程事。
