1. 产品概览

一句话定位

给游客一份「算得准、说得清、可验证、走得通」的行程；给企业一个「看得见、管得住、交得出去」的 AI 生产与治理闭环。

  • toC 游客端 /：水墨主题单页。填一次表单 → 6 个 Agent 协作生成 → 拿到带决策辩论、翻车预演、心情剧本的行程书，并可进入体验中心「追问、投票、换方案」。
  • toB 企业端 /b：暗色工作台。顾问看得见每一单的挂起原因、恢复锚点、审批人、审计流水，能一键白标交付、导出合规 CSV、看安全拦截率与经营曲线。

2.3 toC 功能详解

C-1

智能需求表单

POST /api/plans

功能

12 字段栅格表单：出发地、目的地、人数(1–10+)、预算、日期联动、以图规划(mock)、心情词、偏好、约束。目的地/出发地接 20 城市 datalist；心情词/偏好/约束提供可点选标签；登录用户使用项写入 localStorage，常用项 ★ 金色置顶。

痛点

长表单劝退；用户说不清需求；预算与人数脱节（只填总额，系统不换算）；日期与天数两个框容易填矛盾。

优势

① 纯前端智能化，数据不出域，规避 PII 合规风险；② 预算分项按人数换算（住宿每 2 人一间、打车每 3 人一车）；③ 出发日期 + 天数自动联动返回日期；④ 表单即「结构化 Prompt」，无需脆弱的自然语言抽取。

C-2

实时进度与状态可视化

GET /api/plans/{job_id}

功能

11 态状态机轮询，中文状态文案映射（如 WAITING_BUDGET_APPROVAL → 待预算确认）、百分比进度条、恢复锚点；挂起时橙色 hold banner + 「去确认」入口。

痛点

AI 长任务最怕「转圈无反馈」——用户不知道是在算还是卡死，失败后也不知道从哪一步重来。

优势

进度来自真实 Checkpoint（8% → 100% 随节点推进），不是前端假动画；挂起时显示恢复锚点（如 Reporter），用户能预期「批准后从哪里继续」，把黑盒变白盒。

C-3

行程书（9 章结构）

GET /api/plans/{job_id}/result · html2canvas

功能

①需求摘要 ②每日行程（理由/交通/标签/开放时间）③交通与住宿参考 ④校验与风险提示（分项预算）⑤决策辩论 ⑥翻车预演 B 计划 ⑦心情剧本（填 mood 才有，后续自动顺延为 8/9）⑧工程说明 ⑨Agent 输出索引。配套长图 PNG 导出与旅行盲盒彩头（页面明确标注「行业标配，非创新」）。

痛点

通用大模型给的行程是一整段文字，改一点就要重问一遍，无法核验、无法交付。

优势

产物与状态分离：md 只是展示/导出产物，唯一状态源是 state.json，文件被手改也不会让任务状态漂移；每次写入返回 sha256，交付物可校验完整性；原子写保证读不到「生成到一半」的内容。

C-4

挂起与游客自助确认

POST /api/plans/{job_id}/approval

功能

两类挂起：安全挂起（命中「忽略之前/输出系统提示词/system prompt/泄露密钥」等高危 Pattern）与 预算挂起（Validator 分项估算 > 用户预算）。批准后置 safety_reviewed=true 续跑，或驳回进 REPLAN_REQUIRED。审批带 base_version 乐观锁。

痛点

超预算行程要么直接生成（到现场才发现花超），要么直接失败（用户不知道怎么救）；并发点击会造成重复审批。

优势

把不确定性显式化为可决策的挂起点，而不是悄悄降级或超支；版本不匹配 → 409 VERSION_CONFLICT，状态非法 → 409 INVALID_STATE，重复点击安全；审批事件先写审计再改状态，崩溃也留痕。

C-5

增量重规划「改一改行程」

POST /api/plans/{job_id}/replan

功能

提交变更需求（如「预算改为 3000 元，减少打车」）→ 作为新约束追加 → 生成新 job_id 并返回 diff_summary。核心优化：当目的地 / 天数 / 偏好三者未变时，判定 Researcher/Planner/Itinerary 输出不受 constraints 影响，直接复制父任务 agent_outputs/*.json，resume_from=Validator、进度置 64%，只重算受影响链。

痛点

改一个预算就重跑整条链，成本与延迟翻倍，且行程「整体漂移」——只想改预算，结果景点全换了。

优势

mock 口径实测耗时降约 23%，real 模式因跳过 3 个节点的 LLM 调用收益放大；结果稳定——未受影响节点输出逐字节复用，改预算不会顺带改掉满意的景点；复用记录写审计（incremental_reuse）可追溯。

C-6

行程体验中心（7 子模块）

/debates · /debate/live · /debate/vote · /guides · /dialogue · /swarm · /counterfactual

功能

决策辩论：三议题双栏论点 + 最终取舍。直播辩论：SSE 流式推送 8 句交替发言，游客投票（票数回写 travel_plan.md 第 9 章）。名导团：杜甫/本地吃货/亲子妈妈点评 + 多轮追问。虚拟游客：3 种人格试玩判定。反事实后悔药：放弃 A 换来了 B 对照卡。地图模式：Leaflet + 舒适度。周边服务：美食/车位/厕所按距离排序。

痛点

AI 给结论不给理由，用户不信也不敢用；可解释性做成静态文字没人看；攻略千篇一律缺角色视角；行程纸面完美实际走断腿；用户总怀疑「是不是漏了更好的」。

优势

事实底座全部取自前序 Agent 的结构化输出（选了什么、放弃什么、预算数字、校验结论），LLM 只组织语言、不编事实，mock 模板同样引用真实数字；流式直播把解释变成内容消费，投票把用户拉进决策环且落审计；踩点判定基于真实计算的 commute_minutes（>120 分钟即提示减景点）。

C-7

行程地图模式 + 舒适度

GET /api/plans/{job_id}/map

功能

Leaflet 渲染每日景点坐标（在线用 OpenStreetMap 开放瓦片，断网自动降级为坐标示意图），附舒适度等级（舒适 / 一般 / 拥挤）。

痛点

看文字行程看不出景点之间到底多远，容易把两个远郊区排在同一天。

优势

断网可降级，保证演示不翻车；舒适度由「景点名 + 天数」确定性哈希生成，同一行程多次查询结论一致；舒适度明确标注为演示口径，不假装是真实客流。

C-8

周边服务（美食 / 车位 / 厕所）

GET /api/plans/{job_id}/nearby?kind=food|parking|toilet

功能

对行程前 3 个已选景点查询周边 POI，按 distance_m 升序聚合返回。

痛点

行程只到「景点」粒度，到了现场找不到吃饭、停车、洗手间。

优势

静态演示 POI + 真实 haversine 距离计算与排序，"排序"这件事是可信的；输入 kind 白名单校验，非法值返回 400。

C-9

旅行服务大厅（5 窗口）

GET /api/services/{train|flight|attraction|merchant|entertainment}

功能

车票 / 机票 / 商家 / 景点 / 娱乐五个窗口，班次、票价、商户、排期均为本地静态估算生成，页面明确提示「非真实交易与实时数据」。

痛点

行程与预订割裂，用户拿到行程还要自己开 5 个 App。

优势

用最小成本补齐「行程 → 服务」入口，演示闭环完整；同时明确不接第三方支付与真实票务（GET /api/integrations/status：地图=本地估算、搜索=local、OCR=mock、支付=禁用），规避合规与授权风险。

C-10

登录注册门禁 + 本地长期记忆

POST /api/auth/login · /register · GET /api/auth/me

功能

山水主题登录/注册弹窗（tab 切换），HMAC token（含 username / role / exp）；toC 演示账号 旅者 / 123456，toB admin / wl2026。登录后的表单使用项进入 wlMemory_<用户名> 长期记忆。

痛点

无门禁就无法演示「客户归属 / 租户隔离 / 权限」这套企业级能力。

优势

AUTH_ENABLED 开关式设计：关闭零摩擦演示，开启强制 Bearer 校验；演示级实现不假装是生产 IAM（诚实声明见第 7 章）。

C-11

水墨山水视觉主题 + 程序化素材

frontend/media/* · backend/scripts/make_ink_backdrops.py · make_scenery_video.py

功能

全页水墨背景（页头 ink-hero、正文宣纸底纹 ink-body、页脚墨山 ink-foot）+ 登录页 12 秒无缝循环视频背景 scenery.mp4（约 0.6MB）。

痛点

素材要么有版权风险，要么下载要登录、会员专享（项目曾尝试从千图网取素材，遇登录墙且多数需授权，未绕过）。

优势

全部由 Python 脚本程序化渲染生成——零版权风险、断网可跑、体积可控；视频加载失败自动降级为 CSS/SVG 动画山水，不会开天窗；要换真实授权图片，覆盖同名文件即可。

4. 双端共享的平台能力（后端引擎）

4.1 多 Agent 分工详解

口径澄清：代码注册表 plan_processor.agents 实为 6 个 Agent（Researcher / Planner / Itinerary / Validator / Debate / Mood）+ 1 个 Reporter 汇总节点。仓库内 README.md 称「4 个核心 Agent」、travel_plan.md 工程说明称「5 个 Agent」，均与代码不符，属文档滞后（见第 8 章瑕疵 ④）。

4.1.1 为什么是 6 个，而不是 1 个或 8 个

拆分的唯一判据是输出契约是否不同，而不是「看起来像几件事」。

方案问题
1 个全能 Agent一次调用要同时完成检索、编排、算路、算钱、解释、叙事，任一步出错都无法定位与重跑；改预算要重算全部；无法做节点级复用
8 个物理 Agent检索/编排、解释/叙事职责高度耦合，拆开后传递开销大于收益；且每个节点都要写 Checkpoint，IO 与复杂度翻倍
6 个（当前）每个 Agent 都有独立且可验证的输出契约：候选集 → 日程骨架 → 时空落地 → 质量判定 → 解释 → 叙事。职责边界恰好落在「可单独重跑」的接缝上
关键设计：只有 2 个 Agent 调 LLM（Debate、Mood），前 4 个全是确定性本地计算。三个直接收益——断网可跑、成本可控、结果可复现。

4.1.5 Agent 之间的契约

context = {
    "user_input": {...},       # 只读，任何 Agent 都不得修改
    "outputs": {"Researcher": {"agent":..., "status":..., "payload":{...}}, ...}
}
  • 单向数据流：Agent 只能读 user_input 和前序 outputs，不反向修改，不横向调用兄弟 Agent。
  • 落盘即契约：每节点完成 → save_agent_output() 写 agent_outputs/<name>.json → 相对路径登记进 state.json["agent_outputs"]。
  • 回灌机制：断点恢复时 _load_completed_outputs() 按登记路径反序列化，把已完成节点的输出原样回填进 context，后续 Agent 无感知地继续执行。
  • 进度契约：mark_running(节点, min(index*15+8, 82)) → mark_node_done(节点, min(index*15+23, 88))，进度由真实节点推进驱动，不是前端动画。

4.3 断点续跑与 Crash Recovery

  • Checkpoint：每个节点完成即写 agent_outputs/<agent>.json，并在 state.json 记录 completed_nodes、last_success_node、resume_from、progress。
  • 原子写 + 校验：AtomicWriter 采用临时文件 + rename；state.json 带 .sha256 伴生文件。
  • 启动恢复：startup 事件调用 recover_pending_jobs()——QUEUED/RUNNING 自动重新入队并从 resume_from 继续；终态（COMPLETED/FAILED/CORRUPTED/REPLAN_REQUIRED）跳过；挂起态等人工；state.json 解析失败或 sha256 校验不过 → 标记 RECOVERY_REQUIRED。
  • 幂等兜底：processor 入口先判 COMPLETED 直接返回；按 job_id 取线程锁，Redis 模式下叠加分布式锁，重复投递安全。
痛点 / 优势：AI 长任务跑几十秒到几分钟，进程一重启就前功尽弃，用户体感是「提交后永远转圈」。本系统恢复的是调度而非重跑整条链——已完成的 Agent 输出直接复用，做到真正的「从断点继续」。

4.4 安全护栏

  • 输入扫描 safety_scan → 高风险 block → 挂起 + 通知；中风险 sanitize（替换为「[已移除风险片段]」）。
  • 高危 Pattern（8 条）：忽略之前 / 忽略以上 / 输出系统提示词 / system prompt / ignore previous / developer message / 泄露密钥 / 绕过审核 / 不要告诉用户。中危（4 条）：base64 / 隐藏文本 / html 注释 / 修改预算。
  • 所有安全事件落 audit.log → 看板聚合；拦截与审批进入 Prometheus 计数器。
