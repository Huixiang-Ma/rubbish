# toB 工作台功能判断矩阵

> **目的**:在 6 大功能族 × 40~60 个候选功能中,按三维判断标准筛出"必做"与"可缓",为产品规划提供统一决策依据。
> **版本**:v1.0 / 2026-09-04 / 通用行业最佳实践(不绑定具体项目)
> **适用范围**:任何"AI 能力 + 多租户 + 企业客户"形态的 toB 管控台

---

## 一、判断三维(评估每个功能)

| 维度 | 含义 | 评分标准 |
|---|---|---|
| **对外承诺** | 这个功能是否直接面对客户(企业方),缺失会影响签单/续约 | 高=签单必问 / 中=客户偶尔会问 / 低=客户不会主动问 |
| **对内效率** | 这个功能是否给运营/审核/管理者提效,缺失会让组织变笨变慢 | 高=没它就崩 / 中=能跑但累 / 低=纯锦上添花 |
| **配置化** | 这个功能能否由管理员(非研发)配置完成,无需改代码上线 | 高=纯配置 / 中=半配置半开发 / 低=必须研发改 |

## 二、判断规则

```
必做 = (对外承诺 = 高) AND (对内效率 = 高) —— 至少两个"高"维度
     OR (对外承诺 = 高) AND (配置化 = 高) —— 直接面向客户且能配置
可缓 = 不满足必做条件
不做 = 三个维度都是"低"或明显超出企业当前阶段
```

---

## 三、6 大功能族 × 判断矩阵

### ① 流程与状态治理族(8 候选 → 3 必做 + 3 可缓)

| 功能 | 对外承诺 | 对内效率 | 配置化 | 判断 | 关键说明 |
|---|---|---|---|---|---|
| **审核流程状态图** | 高 | 高 | 高 | ★**必做** | toB 区别于 toC 的核心可视化,管理员可拖拽改流程、设条件分支,客户最常问"你们的审批流长什么样" |
| **工单状态机** | 中 | 高 | 高 | ★**必做** | 多向分派+超时升级+三方协同,客户量一过 50 就离不开它 |
| **异常闭环图** | 中 | 高 | 中 | ★**必做** | 异常发现→告警→处置→复盘全链路,MTTR 直接挂图上,SLA 谈判的硬通货 |
| 客户旅程图 | 高 | 中 | 中 | 可缓 | 主要给运营看,客户偶尔问"用户在哪个环节流失",可与漏斗分析合并 |
| 决策溯源图 | 高 | 中 | 低 | 可缓 | 可解释 AI 的工程化形态,合同级交付物,但开发量大,先用决策日志兜底 |
| 流程模板库 | 低 | 中 | 高 | 可缓 | 锦上添花,前 3 个做完后自然就上 |

### ② 用户与权限族(6 候选 → 3 必做 + 3 可缓)

| 功能 | 对外承诺 | 对内效率 | 配置化 | 判断 | 关键说明 |
|---|---|---|---|---|---|
| **组织/角色/权限树** | 高 | 高 | 中 | ★**必做** | toB 永远先答"谁有权力做什么",RBAC 是基本盘 |
| **多租户隔离** | 高 | 高 | 中 | ★**必做** | 客户问"我家的数据别人看得到吗"的唯一正确答案 |
| **SSO 单点登录** | 高 | 中 | 中 | ★**必做** | 客户 IT 部门第一个集成需求,没 SSO 直接卡在采购流程外 |
| 坐席管理 | 中 | 高 | 高 | 可缓 | 客户量过 100 才显必要性,初期用角色树兜底 |
| 资源配额(Token/算力) | 中 | 高 | 中 | 可缓 | 计费前期用"不限量"销售策略,等毛利率撑不住再做 |
| 登录审计日志 | 中 | 中 | 低 | 可缓 | 等保必备但能用全局审计日志兜底,不必独立成功能 |

### ③ 决策与风险族(10 候选 → 3 必做 + 3 可缓)

| 功能 | 对外承诺 | 对内效率 | 配置化 | 判断 | 关键说明 |
|---|---|---|---|---|---|
| **审核中心** | 高 | 高 | 中 | ★**必做** | 待审/已审/转交/驳回,组织"承担责任"的工程化体现 |
| **决策溯源(简化版)** | 高 | 中 | 低 | ★**必做** | 不需要复杂图,先做"AI 决策的 5 段记录"——输入/检索/候选/辩论/选优——给客户看 |
| **实时风险拦截** | 高 | 高 | 中 | ★**必做** | 高危关键词/价格违规/法律红线,一次失误 = 50 万损失 + 品牌崩塌 |
| 审计追溯 | 高 | 高 | 低 | 可缓 | 完整审计链,合规级要求,初期用结构化日志兜底 |
| 应急熔断/紧急冻结 | 中 | 高 | 高 | 可缓 | 出现重大事故时一键停服,初期用配置中心 + 手动降级 |
| 投票仲裁 | 中 | 中 | 中 | 可缓 | 决策从"个人判断"升级为"组织判断",规模化阶段再做 |

### ④ 客户与业务族(8 候选 → 3 必做 + 3 可缓)

| 功能 | 对外承诺 | 对内效率 | 配置化 | 判断 | 关键说明 |
|---|---|---|---|---|---|
| **客户分级(VIP/标准/试用)** | 高 | 高 | 高 | ★**必做** | 决定 SLA、配额、客服等级的根基,客户问"我是不是高级客户" |
| **品牌白标** | 高 | 中 | 高 | ★**必做** | 客户方 LOGO/域名/话术替换,签大单的"面子工程",纯配置化 |
| **计费对账** | 高 | 高 | 低 | ★**必做** | 客户问"我这月用了多少、付多少钱"的唯一答案,接 SaaS 计费平台 |
| 续约预警 | 中 | 高 | 中 | 可缓 | 客户流失前 30 天主动通知,需历史数据积累,中期再做 |
| 销售漏斗 | 中 | 中 | 中 | 可缓 | 给销售看,可与 CRM 打通而非自建 |
| 客户健康度评分 | 中 | 中 | 中 | 可缓 | 综合分,前期人工判断足矣 |

### ⑤ 数据与洞察族(8 候选 → 3 必做 + 3 可缓)

| 功能 | 对外承诺 | 对内效率 | 配置化 | 判断 | 关键说明 |
|---|---|---|---|---|---|
| **经营看板** | 高 | 高 | 中 | ★**必做** | 高管每周看的"心脏"页,客户来参访必展示 |
| **指标体系管理** | 中 | 高 | 高 | ★**必做** | 北极星+护栏指标统一管,管理员可加指标、改口径,避免"数对不上" |
| **归因分析** | 中 | 高 | 低 | ★**必做** | "为什么这个月完成率掉了"——从"看数"升级到"看懂数" |
| 预测(流失/容量) | 中 | 中 | 中 | 可缓 | ML 模型成本高,需数据积累,中期再做 |
| A/B 实验 | 中 | 中 | 中 | 可缓 | 产品迭代决策需要,需规模日均万级才有意义 |
| 漏斗分析 | 中 | 中 | 中 | 可缓 | 可与归因合并,不必独立 |

### ⑥ 平台与生态族(6 候选 → 3 必做 + 3 可缓)

| 功能 | 对外承诺 | 对内效率 | 配置化 | 判断 | 关键说明 |
|---|---|---|---|---|---|
| **外部集成状态** | 高 | 高 | 中 | ★**必做** | 客户问"我接的支付/地图挂了没",企业管控台必备"依赖透明度" |
| **开放 API** | 高 | 中 | 低 | ★**必做** | 客户 IT 部门的"接入凭证",签大单必备,可先用 OpenAPI 文档兜底 |
| **Webhook** | 中 | 高 | 高 | ★**必做** | 让客户业务系统实时同步事件,纯配置化,边际成本极低 |
| SDK/插件 | 中 | 中 | 中 | 可缓 | 客户技术栈稳定后再做,先服务好头部 3 家 |
| 开发者门户 | 高 | 低 | 低 | 可缓 | 客户基数小(< 20)时做了也没人用 |
| 监控告警(业务级) | 中 | 高 | 中 | 可缓 | 初期用技术监控告警兜底,业务告警规模上来再独立 |

## 四、跨族横切能力(必做 6 个)

横切能力不属于任何一族,但**缺失就说明产品没做完**——必做:

| 横切能力 | 优先级 | 关键说明 |
|---|---|---|
| 通知中心 | P0 | 站内通知 + 邮件 + 短信 + 企业微信/钉钉,事件驱动 |
| 全局搜索 | P0 | 跨客户/方案/工单的统一搜索,Ctrl+K 唤起 |
| 个人工作台 | P0 | 管理员自己的待办/草稿/常用功能入口 |
| 消息推送策略 | P1 | 按角色/事件/时段配置推送规则,避免告警疲劳 |
| 文件管理 | P1 | 客户上传的营业执照、合同附件、导出文件统一管理 |
| 系统设置 | P0 | 平台级参数(品牌名/Logo/域名/计费币种) |

## 五、汇总:18 必做 + 18 可缓 + 6 横切

| 类别 | 数量 | 节奏建议 |
|---|---|---|
| **必做(核心 18)** | 6 族 × 3 = 18 | 3~6 个月内分批交付,按"对外承诺 × 对内效率"双高优先 |
| **可缓(进阶 18)** | 6 族 × 3 = 18 | 业务跑起来后按 ROI 排序,通常 6~12 个月分批 |
| **横切必做** | 6 | 与第一批核心功能同步交付,否则产品"缺筋少骨" |

**18 个核心必做的内部优先级**(按签单影响力):
1. 组织/角色/权限树 + 多租户隔离 + SSO(客户 IT 第一道关)
2. 实时风险拦截 + 审核中心 + 决策溯源(客户业务第一道关)
3. 外部集成状态 + 开放 API + Webhook(客户技术第一道关)
4. 客户分级 + 品牌白标 + 计费对账(客户商务第一道关)
5. 经营看板 + 指标体系 + 归因分析(客户高管第一道关)
6. 审核流程状态图 + 工单状态机 + 异常闭环图(组织内运营第一道关)

## 六、判断的"边界"提醒

| 看起来必做但实际可缓 | 看起来可缓但实际必做 |
|---|---|
| 投票仲裁(组织没大到需要时,徒增复杂度) | **决策溯源简化版**(客户法务/合规必问"AI 凭什么这么决定") |
| 开发者门户(用户基数小时没价值) | **品牌白标**(签大单的临门一脚,纯配置化低投入) |
| A/B 实验(数据量小结论不可靠) | **指标体系管理**(没它多个看板"数对不上"会搞死组织) |
| 客户健康度评分(早期人工判断更快) | **应急熔断**(没它一次大事故就完蛋,纯配置化低投入) |

---

## 七、配套执行原则

1. **必做不全做完 = 客户问起来答不上 = 丢单**
2. **可缓提前做 = 资源错配 = 拖累核心**
3. **横切必做同步 = 必做才有"产品感",否则只是功能堆砌**
4. **每族留 1 个"代表功能"做深**,不要平均用力(代表功能选择:①族=审核流程状态图,②族=多租户隔离,③族=实时风险拦截,④族=计费对账,⑤族=经营看板,⑥族=外部集成状态)

---

**配套原则**:每上一族代表功能,先做"管理者视角的截图 + 走查"再交付——toB 卖的是"组织放心",截图比代码更能让客户买单。
