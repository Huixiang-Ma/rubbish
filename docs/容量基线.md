# 容量基线（P0.5 · mock 版压测）

> 日期：2026-09-06。环境：本地 Windows 开发机（Docker Desktop，`data/` 为 Windows 绑定挂载），
> `LLM_MODE=mock`（零 token 成本）、隔离实例（项目 `wl_loadtest`，端口 8010，独立 Redis，`WORKER_COUNT=2`）。
> 工具：`backend/scripts/load_test.py`（仅统计 `POST /api/plans` 提交：含 state.json 原子落盘 + 入队，不含行程生成）。

## 结果

| 档位 | 总数/并发 | 成功率 | 吞吐 | p50 | p95 | p99 |
|---|---|---|---|---|---|---|
| 1 | 10 / 10 | 100% | 2.3 rps | 265ms | 4.3s* | 4.3s* |
| 2 | 50 / 50 | 100% | 33.0 rps | 988ms | 1.4s | 1.4s |
| 3 | 200 / 64 | **100%（0 错误）** | 26.9 rps | 2.35s | 3.7s | 3.7s |

*档位 1 的 p95 为容器冷启动首请求。

## 结论

1. **提交层不是瓶颈**：200 并发零失败，Redis 队列全部吸收。错误率 0。
2. **当前瓶颈是 Windows 绑定挂载的文件 I/O**（每单 2 次原子写：state.json + sha256）。Linux 云主机上预期 p95 显著低于本表。
3. **生成吞吐与提交无关**：真实 LLM 每单 1-11 分钟，是真正的容量约束。水平扩容路径 = `WORKER_COUNT>1`（Redis 分布式锁已就绪）+ LLM 供应商并发配额。
4. **免费额度拦截在压测中表现符合预期**（首次运行被 429 正确拦截，隔离实例放宽后正常）。

## 复跑方式

```bash
docker compose -p wl_loadtest -f docker-compose.yml -f docker-compose.loadtest.yml up -d backend redis
python backend/scripts/load_test.py --base-url http://127.0.0.1:8010 --total 200 --concurrency 64
docker compose -p wl_loadtest -f docker-compose.yml -f docker-compose.loadtest.yml down
```

压测数据落 `data/jobs_loadtest/`，与生产数据隔离，定期整目录删除即可。

## 生产建议

- 单云主机（4C8G）按本基线外推：提交层可承载数百并发提交；系统瓶颈在 LLM 侧，规划容量时按"Worker 数 × LLM 供应商并发上限"估算日单量。
- 达到数千 DAU 前，提交层无需优化；届时优先事项是把 data 卷迁到 Linux 本地盘（或直接用 PG 为主库）。
