## 新发现（既有缺陷，未修，等用户决策）

**smoke_test 第一条 happy path 失败**：「北京 3 天 5000 元 + origin 上海」实测预估 5714 元 → 进 `WAITING_BUDGET_APPROVAL`，等不到 COMPLETED。

根因在 `travel_context_service.recommend_hotel()`：
```
allowance = budget - intercity_cost - days*150
```
1. `intercity_cost` 用的是**单人**往返价，实际支出要 × travelers
2. allowance 只扣餐饮，**没扣门票与市内交通**
→ per_night_allowance 虚高 → 住宿总是顶格选「品质型 1000 元/晚」→ 预算被吃光 → 必然超支

连带影响：`README.md` 演示脚本第 1 条「北京 3 天 5000 元 → COMPLETED」实际不成立。

修法建议（未实施）：`recommend_hotel` 增加 `travelers` 参数，`fixed = intercity_cost*travelers + days*150*travelers`，再为门票/市内交通预留约 25% 额度后才分档；需同步改 `validator.py` 的两处调用。

## Agent 清单核实（2026-08-31 晚，逐行读码确认）

**核心结论：项目只有 1 条 Agent 管线，toC / toB 两端共用；toB 端没有独立 Agent。**

- 注册表 `backend/app/services/plan_processor.py:27` → 6 Agent 串行：Researcher → Planner → Itinerary → Validator → Debate → Mood，外加 Reporter 汇总节点（非 Agent，唯一写 travel_plan.md 的组件）。
- 只有 Debate、Mood 调 LLM（`LLMClient.try_generate_json`，失败落确定性模板）；前 4 个全是本地确定性计算 → 断网可跑、可复现。Mood 在 `user_input.mood` 为空时被跳过。
- **Validator 是唯一能让流程停下的 Agent**：`approval_required` → WAITING_BUDGET_APPROVAL，此挂起同时供 toC 游客自助确认与 toB 待审队列（`GET /api/approvals/pending`，可按 tenant 过滤）消费。另一条挂起路径：`SafetyService.scan_user_input` → WAITING_SAFETY_REVIEW。
- **toC 的"角色化 Agent"不在 agents/ 目录**，在 `services/experience_service.py`：名导团 3 角色（带历史多轮对话）、虚拟游客 3 人格踩点、反事实后悔药、直播辩论 SSE + 投票。属消费层虚拟角色，非管线节点。
- **toB 能力全部由 API/Service 承担、非 Agent**：`api/admin.py`（待审队列/审计 CSV/统计）、`api/plans.py` 的 `/export` 白标交付（品牌块 + 原稿 sha256）、`api/auth.py`（HMAC token + require_admin + tenant/customer）、`safety_service.py`+`api/safety.py`（拦截率）。
